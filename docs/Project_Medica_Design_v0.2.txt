Minecraft 1.21.4 Fabric 医学模拟模组
项目设计与开发记录

文档版本：V0.2
项目状态：概念设计与早期功能开发阶段
目标平台：Minecraft Java Edition 1.21.4
目标模组加载器：Fabric（暂定）

一、项目愿景

1.1 核心目标

开发一款面向 Minecraft Java Edition 1.21.4 的深度医学模拟模组，让玩家不只是简单地损失生命值或获得一个负面状态，而是能够经历疾病发生、症状表现、诊断、治疗、病情变化与康复的完整过程。

模组计划融合以下内容：
- 疾病与病程模拟
- 症状识别与临床诊断
- 药物、草药与制药系统
- 民间医疗与随机事件
- 医生、药师等村民职业
- 急救与危重病情处理
- 医疗资源收集、制作和交易
- 可扩展的疾病、药物和配方数据库

1.2 设计原则

1. 重视过程：疾病不是单一的状态效果，而是可以发展、缓解、恶化和康复的过程。
2. 鼓励推理：玩家应当根据症状、病程和已有信息判断可能的病因。
3. 多种治疗路径：玩家可以自行采药制药，也可以向医生或药师寻求帮助。
4. 保留生存挑战：严重疾病需要及时处理，但不应完全依赖运气。
5. 方便后续扩展：新疾病、新药物、新草药和新交易内容应尽量采用模块化、数据驱动的设计。
6. 兼顾游戏性：医学机制需要足够深入，同时避免过度繁琐或让玩家失去继续游戏的能力。


二、疾病模拟系统

2.1 基础疾病机制

计划为疾病设计独立的病情数据，而不只依靠 Minecraft 原版状态效果。

每种疾病未来可以包含：
- 疾病名称与内部 ID
- 病因或触发条件
- 潜伏期（如适用）
- 初期、中期、重症等病程阶段
- 对应症状
- 病情发展速度
- 恶化与缓解条件
- 诊断方法
- 可用药物和治疗方法
- 康复条件
- 复发或后遗影响（可选）

以上为目标设计，具体疾病规则尚未确定。

2.2 病情严重程度

暂定采用以下严重程度分级：

等级 1：轻症——通常可自行缓解或通过基础药物治疗
等级 2：中症——需要更有针对性的治疗
等级 3：重症——需要较有效的药物或专业医疗服务
等级 4：垂危——需要尽快接受急救或高级医疗干预

严重程度与病程阶段是两个不同的概念，未来需要决定它们是独立参数，还是部分关联。

2.3 诊断系统

计划让玩家逐步掌握疾病信息，而不是始终直接显示完整病名。

可能采用的机制：
- 根据症状推测病因
- 使用诊断工具或检查项目
- 向医生村民咨询
- 根据病程变化修正判断
- 通过病历记录患者信息和治疗经过

待决定：玩家是否能够直接看到疾病名称、是否需要进行检查，以及不同难度下隐藏多少信息。


三、野生草药与采集系统

3.1 核心构想

在 Minecraft 世界中新增可以自然生成的草药或野生药用植物。玩家探索世界时可以采集它们，并将其用于直接缓解症状或进一步制药。

整体流程（总体构想）：
探索世界 → 采集草药 → 获得或解锁药方 → 传统煎制或规范加工 → 使用药物或出售药品

第一种实际开发中的草药为薄荷。当前开发进度见“开发日志”。薄荷的目标生长地已在设计 TXT 中更新，但自然生成代码尚未完成。
草药的具体生成群系、稀有程度、采集工具和再生机制仍可继续调整。

3.2 第一批候选草药

以下均为游戏设计提案，不代表现实医疗疗效。

- 薄荷：提供清凉效果，降低中暑或热相关疾病的风险。优先级：高。
- 止血草：用于制作止血敷料，处理出血状态。优先级：高。
- 洋甘菊：用于制作舒缓类茶剂或基础药物。优先级：中。
- 紫锥花：用于制作虚构的免疫支持类药剂。优先级：中。
- 柳树皮：用于制作缓解疼痛或不适的药物。优先级：中。
- 苦根：用于制作虚构的解毒或驱虫类药物。优先级：中。

草药名称、功能、稀有度和实际效果均允许在开发过程中修改。

3.3 草药使用方式

计划探索两种使用方式：
- 直接使用：操作简单，但效果可能较弱、持续时间较短或适用范围有限。
- 加工制药：需要配方和材料，效果更加明确，适合处理特定疾病或症状。

例如，薄荷未来可以作为传统煎制或规范制药的材料；清凉、防暑等具体游戏效果仍属于待实现设计，不能视为已经完成的功能。

3.4 两条制药路线：传统土方子与规范制药

传统土方子（中药风格）：
- 主要使用采摘到的草药，直接投入炼药锅进行煎制，减少前期加工门槛。
- 煎制完成后，药液保存在炼药锅内。
- 玩家手持 Minecraft 原版木碗（Bowl）右键炼药锅，每次取得一碗对应的中药。
- 一个炼药锅最多储存四碗已煎制完成的中药；每次取药只取一碗。
- 同一锅的四份药液属于同一配方，避免药方混淆。
- 传统土方子可能成功、无效，或在治疗失败时引发副作用。
- 以上为已讨论确定的设计方向；炼药锅自定义状态、煎制计时、药碗成品注册和交互代码尚待实现。

原版炼药锅并不原生支持上述自定义药液储存与配方系统，需要模组代码扩展其交互及状态保存。应避免在未实现前将其描述为已有功能。

规范制药（西药风格）：
- 由医生村民、药师等渠道提供成品药物、原料或配方。
- 原料需要经过研磨等加工步骤，再进行混合或其他制药流程。
- 计划使用新增的制药台及未来可能加入的研磨设备。
- 设计目标是让规范药物的用途和疗效比民间土方子更明确、更稳定；具体数值与例外情况待平衡。

两条路线并非简单的强弱关系：传统路线应当低门槛、适合探索与应急；规范制药更依赖设备、配方与材料。未来可以让部分疾病或症状更适合特定路线。

生长环境：温暖湿润、阳光充足。

主要生成地：

次要生成地：

四、制药系统

4.1 新工作方块：制药台

计划新增专门用于药物加工的工作方块。

制药台的候选功能：
- 根据已解锁药方制作药品
- 消耗对应草药和其他材料
- 支持多种药物配方
- 为未来添加复杂制药流程预留接口

具体界面、材料槽位、制作时间和失败机制尚未确定。

规范制药的总体方向是先研磨或加工原料，再按配方制成药物，与直接投入草药煎制的传统土方子路线区分。

4.2 药方系统

药方是玩家从收集材料过渡到自主制药的关键。

计划采用以下流程：
1. 玩家通过交易、探索或其他事件获得药方。
2. 使用药方物品后，永久解锁对应配方。
3. 玩家收集配方要求的材料。
4. 在制药台制作药物。
5. 将药物用于自身或提供给其他玩家（如未来支持多人游戏）。

建议后续尽量将配方内容存储为数据文件，以便增加或调整配方时减少对核心代码的修改。

待决定：药方是否允许重复交易、能否分享、是否有稀有等级，以及药物是否需要保质期。


4.3 搅拌交互（保留设计，暂不实现）

记录日期：2026-10-27。用户同意保留此设计，当前不添加搅拌或失败产物代码。

当前已实现的薄荷茶流程：满水炼药锅投入薄荷，正下方由燃烧的营火或岩浆块供热，自动累计冲泡时间；移走热源暂停，恢复后继续，完成后用玻璃瓶盛取四份。用户已确认保留当前配方与基础饮用收益作为现阶段基准，详见 4.5；将来仍可根据实际体验调整。

保留的交互方向：
- 玩家手持木棍右键正在冲泡的炼药锅，可以触发搅拌。具体动作、音效、粒子与提示在实现时确定。
- 薄荷茶等日常饮品不强制搅拌。不搅拌也应正常自动完成，不会因为玩家离开或没有操作而变成失败品。
- 可选奖励方案：主动搅拌一次略微加快冲泡，每锅最多生效一次，避免要求玩家连续点击。是否采用加速以及具体数值均待确定。
- 将来部分特殊药品可以要求搅拌，但必须在药方或制作提示中事先说明要求。尚未确定哪些药品采用该规则。
- 对需要搅拌的配方，优先考虑在对应阶段暂停等待，完成搅拌后继续，避免错过短暂操作窗口就损失整锅材料；细节待实现前确认。
- 因未搅拌而产生失败药品，仅保留为未来高难度配方的候选，不用于当前薄荷茶，也未确认必须采用。
- 为未来自动化预留兼容方向，不在当前阶段锁定自动搅拌装置或漏斗实现方案。

实现边界：此处只记录设计，不改变当前自动冲泡、热源检查、暂停续泡和玻璃瓶盛取行为。后续决定实现时，先确认具体配方与玩家提示，再编写代码和测试。


4.4 制药自动化（暂缓）

决定日期：2026-10-27。用户决定先搁置制药自动化，待想到合适方案后再讨论；此决定取代此前将漏斗按需投料作为下一步的建议。

暂缓范围：
- 漏斗按需投入草药。
- 自动补水，包括发射器对炼药锅使用水桶的设想。
- 自动装瓶、自动取出成品与整条生产线的循环运行。

原因与边界：
- 用户查阅 Minecraft Wiki 后反馈，发射器功能说明标注其不能按原设想向炼药锅装填水桶；原计划的自动补水路径因此不采用。此处记录用户提供的资料与决策原因，本次未另行进行原版行为测试。
- 暂缓属于玩法设计与开发优先级决定，不表示模组技术上无法扩展这些交互；目前不新增相关扩展。
- 保留已实现的手动加水、手动投料、自动计时冲泡和手动玻璃瓶盛取。自动冲泡仍正常工作，不要求玩家自己计时。
- 搅拌继续按 4.3 保留设计、暂不实现。重新启动自动化开发前，先确认完整的供水、投料与出品方案。


4.5 薄荷茶的配方与基础饮用收益（当前基准已确认）

确认日期：2026-10-27。用户同意保留当前配方和基础饮用收益，本次不调整玩法数值。

- 定位：日常饮品。清凉、防暑等效果留待相应系统具备基础后另行讨论，当前没有此类治疗或防护效果。
- 每锅材料：两个薄荷与一满锅水。
- 热源：锅正下方燃烧的营火或岩浆块；移走热源暂停，恢复后续泡。
- 冲泡时间：累计加热 400 游戏刻，正常速度约 20 秒。
- 每锅产出：四瓶薄荷茶，手持玻璃瓶逐份盛取。
- 每瓶饮用收益：恢复 2 点饥饿值，饱和系数 0.3，满饥饿值时也可饮用。
- 容器与携带：每组最多 16 瓶，饮用后返还玻璃瓶。
- 自动化仍按 4.4 暂缓；搅拌仍按 4.3 保留设计、暂不实现。

以上为用户确认的现阶段基准，不表示未来不可根据生存体验调整。下一开发目标尚待确定，不将建议中的成就或其他新玩法标记为已采用或已实现。


五、村民医疗职业

5.1 医生村民

计划更新现有村庄医生职业的交易表，或新增独立医生职业。具体实现方式需要根据现有职业机制和兼容性决定。

医生的主要职责是医疗服务，而不只是出售商品。

候选交易与服务：
- 低级：基础药物、常见草药、初步诊断。
- 中级：更多药物，以及有概率出现的药方。
- 高级：稀有药方、较完整的诊断、收费治疗和急救服务。

医生达到足够高的职业等级后，有概率刷新特定药方。具体概率与交易次数需要平衡。

收费治疗：
当玩家受伤或患病时，可以支付绿宝石，向医生购买相应的治疗服务。治疗内容可根据玩家当前状态提供不同选择，例如治疗轻症、缓解症状、降低病情严重程度，或在满足条件时提供完整治疗。

垂危状态下的人道主义救援：
当玩家处于“垂危”状态时，医生可以触发特殊救援机制。

候选结果：
1. 稳定病情：暂时阻止病情继续恶化。
2. 降低严重程度：将垂危状态降低为重症。
3. 成功救治：解除危急状态，使患者进入恢复阶段。

救治成功率可以受到医生等级、玩家病情和治疗费用等因素影响。

设计原则：危重救援可以存在失败概率，但不能让玩家长期陷入毫无解决办法的状态。可以考虑失败后提高下一次救治成功率，或确保每次救援至少有一定概率稳定病情。

5.2 药师村民

计划新增独立的药师职业。

核心职责：
- 主要出售成品药物
- 可以出售常用药材或制药材料
- 与制药台绑定工作站
- 不负责疾病诊断
- 不提供直接治疗或急救服务

医生负责判断病情和提供医疗服务；药师负责药品与制药资源供应。

药师是否拥有独立的交易等级、稀有药品库存和补货机制，后续再决定。


六、赤脚医生与民间医疗

6.1 核心构想

新增一种类似流浪商人的特殊 NPC：赤脚医生。

赤脚医生在世界中随机出现，为玩家提供较容易接触到的民间医疗资源。

6.2 出现机制

候选设计：
- 在合适的区域随机刷新
- 在玩家附近出现，但不应过于频繁
- 存在停留时间，之后离开
- 具有独立的刷新冷却时间
- 生成概率和停留时间可调整

具体生成规则尚未确定。

6.3 商品与服务

赤脚医生可能提供：
- 常见野生草药
- 基础药剂
- 民间土方子或特殊药方
- 收费治疗服务

民间治疗具有一定的成功概率。

候选平衡规则：
- 轻症的治疗成功率较高
- 中症可能得到缓解或治疗
- 重症的治疗效果不稳定
- 垂危时可能只能提供有限急救，不能保证治愈

为了避免玩家觉得系统完全依赖运气，应当向玩家提供大致的可靠性提示，并让不同治疗方案具有清晰的风险与收益差异。

民间土方子应属于游戏中的虚构机制，不应被设计成现实医学建议。

6.4 土方子治疗结果与相关成就

土方子的治疗结果计划分为三类：
1. 成功：治愈疾病，或成功降低疾病严重程度。
2. 无效：没有改善，也不额外施加惩罚。
3. 失败并产生副作用：治疗未成功，并给玩家施加负面效果。

成就候选与触发条件：
- “灵丹妙药”：玩家使用土方子，成功治愈疾病或成功降低病情严重程度。
- “是药三分毒”：玩家使用土方子治疗失败，且此次失败实际导致负面效果。单纯拥有其他来源的负面效果不触发。

两项成就均应根据本次土方子的实际治疗结果触发，而不是仅检查玩家是否生病或是否具有负面状态。成就解锁后只记录一次，但不影响后续治疗判定。具体概率暂不锁定。


七、创伤与其他医疗状况（规划）

除疾病外，医疗系统还计划支持骨折等创伤。建议现在纳入整体架构规划，但暂缓实现代码，待第一种疾病的完整流程跑通后再开发。

初步分类：
- 疾病：可具有病因、潜伏期、症状、病程、诊断、药物治疗与康复过程。
- 创伤：例如骨折、扭伤、开放性伤口，通常由坠落、攻击或其他事件触发；需要固定、包扎或专门治疗。
- 急性生理状态：例如失血、脱水、体温异常或缺氧，可能由环境、伤害或其他系统触发。
- 诊断与医疗服务：作为疾病、创伤及其他医疗状况共用的服务层。

骨折的初步设计提案：
- 可能由高处坠落或特定强力伤害触发。
- 可影响移动、跳跃或战斗能力。
- 可通过检查或医生服务辅助诊断。
- 夹板或固定装置作为候选治疗方式；止痛类药物可以缓解部分症状，但不应直接替代固定。
- 固定后经过一定时间逐渐恢复。

以上骨折规则均为初步提案，触发阈值、症状、治疗物品与恢复时间尚未确定。疾病和创伤应共享通用的医疗状况管理、严重程度、诊断与服务框架，同时保留各自独立规则。


八、医疗经济与玩法闭环

计划让不同系统互相联系，形成完整的医疗资源循环：

1. 玩家探索世界并采集草药。
2. 玩家从医生、赤脚医生或其他渠道获得药方。
3. 玩家在制药台制作药物。
4. 玩家使用药物治疗疾病。
5. 缺少材料时，可以向药师购买药材或成品药。
6. 遇到难以处理的病情时，可以付费向医生求助。
7. 面对紧急情况时，可以寻找具备急救能力的医生。

玩家可以选择不同的发展路线：
- 采药路线：依赖探索与资源收集。
- 制药路线：依赖药方、材料与生产。
- 交易路线：通过绿宝石购买医疗资源。
- 医疗服务路线：通过 NPC 获得诊断、治疗与急救。

后续可以根据生存难度、资源稀缺度和药物成本调整各路线的可行性。

十一、成就与特殊彩蛋设计

以下为已讨论的成就/彩蛋候选；具体图标、进度条件、是否隐藏以及实现代码仍待开发。

11.1 成就系统的范围与原则

成就用于记录玩家达成的医疗里程碑、探索发现和隐藏彩蛋；它不应替代疾病、治疗、交易或村民行为本身的游戏逻辑。

- 实现形式：采用 Minecraft 原版进度（Advancement）系统；每项成就应有独立 JSON 文件、内部 ID、显示名称、描述、图标、父节点与触发条件。
- 记录粒度：成就进度按玩家分别保存。多人游戏中，某个玩家解锁成就不应自动为其他玩家解锁，除非未来明确设计为团队目标。
- 判定位置：涉及治疗结果、病情变化、交易归属、医生服务或村民回避的成就，应在服务端根据实际事件结果判定；客户端只负责显示提示和进度界面。
- 触发原则：只在本模组明确记录的行为和结果满足条件时解锁。不得用“玩家当前带有负面效果”“附近存在苹果”等间接状态代替一次具体行为结果。
- 可重复行为：同一成就只解锁一次；解锁后，原有治疗、交易、寻路和随机判定仍照常进行。
- 奖励策略：默认只提供原版成就提示、进度页和描述，不直接奖励治疗物品、绿宝石或经验，避免利用成就重复刷资源。若未来需要物质奖励，必须逐项明确并验证不可重复领取。
- 可见性：常规玩法里程碑默认可见；彩蛋和需要玩家自行发现的条件可设为隐藏。隐藏只影响未解锁时的显示，不应改变触发规则。
- 数据驱动边界：显示文本、图标、父子关系和可由原版条件表达的简单收集/制作条件应放在数据文件；依赖模组治疗结果的条件需要自定义触发器或由服务端代码授予进度。

11.2 推荐成就树与前置关系（候选）

建议先创建一个根节点“医学之始”，再将成就按玩法拆成四条分支。名称可后续修改，内部 ID 一旦发布应尽量保持稳定。

- 根节点：医学之始（候选 ID：`root`）。建议由首次获得薄荷或其他基础草药触发，用于开启本模组的成就页。
- 草药与制药分支：久病成医、神农尝百草、自给自足、药到病除。
- 土方子与风险分支：灵丹妙药、是药三分毒。
- 医疗服务与救援分支：白衣天使、妙手回春、幸存者。
- 诊断与交易分支：福尔摩斯、我不是药神、医药大亨、悬壶济世。
- 彩蛋分支：一天一苹果。建议作为隐藏节点，放在医生服务分支下或以根节点为父节点。

“首次成功制作药物”需要在传统煎制和规范制药完成后统一定义。建议将“久病成医”设为首次获得任一由玩家自行完成的药物成品；单纯购买、拾取或使用他人制作的药物不触发。该定义仍待确认。

11.3 治疗与服务结果的成就判定数据

当前设计中的治疗相关成就不能仅靠原版物品、状态效果或交易条件准确表达。实现疾病和治疗系统时，应由服务端产生一次明确的结果记录，至少包含：

- 触发者玩家与受治对象。
- 治疗来源：传统土方子、规范药物、医生服务、赤脚医生服务或其他来源。
- 使用的配方、药物或服务 ID。
- 治疗前后的医疗状况、严重程度和病程阶段。
- 结果枚举：成功、无效、失败并产生副作用；医生救援还应能区分稳定、降低严重程度和完全救治。
- 本次结果实际施加的副作用或状态变化。
- 是否由玩家亲自收集材料、制作药物或完成交易，供“自给自足”“我不是药神”等条件使用。

上述记录既服务于成就触发，也能服务于病历、调试日志与多人环境的一致性校验。成就系统不应自行重新计算治疗概率或病情结果。

11.4 已列成就的最低触发定义与验收要求

- 灵丹妙药：本次传统土方子结果为成功，且确实治愈疾病或降低严重程度。验收：无效结果、只获得其他来源的增益或只打开药碗均不触发。
- 是药三分毒：本次传统土方子结果为失败并实际施加副作用。验收：治疗无效、玩家原本已有负面效果、或副作用被其他机制取消时均不触发。
- 妙手回春：医生服务在玩家处于垂危时，实际稳定病情、降低严重程度或完成救治。最终采用哪一种结果作为门槛尚待确认；实现前必须写入精确条件。
- 我不是药神：玩家出售自己制作的药物给医生或药师。验收：转售购买、拾取或其他玩家制作的药物不触发；需要定义“自己制作”的物品来源记录如何保存。
- 一天一苹果：医生因该玩家背包中至少有一个普通苹果而开始回避，并且该玩家首次进入可观察到的回避范围。验收：附近箱子中的苹果、金苹果、或医生因其他原因移动均不触发；玩家垂危时的救援优先级高于此彩蛋。
- 其他候选成就：在实现前必须为每项补齐“谁触发、何时触发、一次行为还是累计统计、是否隐藏、是否需要奖励、如何在开发客户端复现”的验收定义。

11.5 成就资源与测试清单

每项成就进入开发前应建立以下清单：

- 内部 ID、中文显示名称、描述、图标、背景页、父节点和可见性。
- 原版 JSON 条件或自定义服务端触发方式。
- 多人归属规则、是否需要累计计数、解锁后是否保留统计。
- 正向测试：满足精确条件时只为目标玩家解锁一次。
- 反向测试：相似但不满足条件的情况不解锁。
- 回归测试：成就触发不会改变治疗概率、药物消耗、交易结果、村民寻路或疾病数据。

开发顺序建议：先在薄荷与第一种完整药物流程完成后，实现根节点和“久病成医”；随后实现依赖明确治疗结果记录的“灵丹妙药”“是药三分毒”；村民、交易和疾病系统稳定后，再实现其余成就与苹果彩蛋。


成就候选：
- “久病成医”：首次成功制作药物；可讨论是否同时覆盖传统煎制与规范制药。
- “妙手回春”：玩家处于“垂危”状态时，医生村民治疗成功并实际稳定病情。
- “我不是药神”：玩家将自己制作的药物出售给医生或药师村民；仅转售购买来的药品不触发。
- “灵丹妙药”：使用土方子成功治愈疾病或降低严重程度。
- “是药三分毒”：使用土方子失败并因此获得负面效果。
- 其他候选：“药到病除”（首次正确使用药物治愈疾病）、“自给自足”（自行收集所需材料并制作药物）、“神农尝百草”（收集所有基础草药）、“福尔摩斯”（通过症状/检查正确识别疾病）、“幸存者”（从重症康复）、“白衣天使”（首次接受医生成功治疗）、“悬壶济世”（累计治疗一定数量的患者）、“医药大亨”（出售一定数量的自制药物）。

苹果彩蛋（已讨论的设计方向）：
- 当玩家背包中携带至少一个普通苹果时，医生村民会主动与玩家保持距离或尝试避开玩家。
- 仅检查玩家背包，不检查附近箱子。
- 玩家吃掉、丢弃或存放苹果后，医生恢复正常行为。
- 若玩家处于“垂危”状态，医生忽略苹果回避规则并尝试实施救援。
- 回避行为应受距离限制并沿用正常寻路，避免医生无限逃离。
- 隐藏成就候选：“一天一苹果”：首次观察到医生村民因玩家携带苹果而避开玩家。
- 彩蛋灵感来自英语俗语 “An apple a day keeps the doctor away”，作为游戏笑点，不作为现实医疗建议。
